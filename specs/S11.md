# S11 内部エンドポイントの共通の形、`/status`、`/metrics`

`/` の案内、応答の形の版 `schema`、`/status` の窓と欄 (上限・ホスト別・接続元別・名前解決・RSS の内訳・直近の分位点・自己ベンチ・転送速度)、`/metrics` の系列。

> T37.4 で `docs/features.md` の「ヘルスチェック & メトリクス & 操作」の頭と `/status` の欄の項目、`README.md` の「動作確認 (curl)」の後ろの説明 (`schema`・`/status`・`/metrics`)から移した (本文は移す前と同じ。位置で指していた所だけ、仕様の番号と文書の名前に直した)。

**ヘルスチェック & メトリクス & 操作**:

- `/` (エンドポイントの一覧。ブラウザでプロキシの URL を開いた人への案内。`--lite` でも出ます)
- **応答の形の版 `schema`**: JSON を返す口はどれも先頭に `"schema":1` を持ちます
  (読む道具が「この JSON はどの版か」を推測しなくて済むように。版の履歴は S11 の「応答の形の版 (`schema`)」の表)
- `/config` (**効いている設定とその出どころ**。S7)

**応答の形の版 (`schema`)**: JSON を返す口はどれも、**応答の先頭に `"schema":N`** を持ちます (整数。`/proxy.pac` と
`/metrics` と HTML のページは JSON ではないので付きません)。エラーの応答 (400 / 404 / 405) にも
同じ版が入ります。`/snapshot` は**外側と各部の両方**に持ちます (各部はそれぞれの口の出力
そのものなので、切り出して 1 本の応答として読めます)。

```bash
curl -s http://127.0.0.1:8080/status | head -c 32     # {"schema":1,"status":"ok","versi
```

読む道具 (`scripts/status-diff.py` / `scripts/snapshot-diff.py` / `scripts/check-dashboard.js`) は
この版で分岐します。**版を持たない古い出力は「版 0」として今までどおり読めます**
(鍵の有無から形を推測する道)。定義は `crates/metrics/src/metrics.rs` の `SCHEMA` の 1 か所です。

| 版 | 日付 | 何が変わったか |
|---|---|---|
| 0 | 〜2026-09-16 | `schema` が無い。読む道具は鍵の有無 (`parts` があるか、`hosts` が object か) から形を推測する |
| 1 | 2026-09-16 | 全 JSON の先頭に `"schema"` を足した (タスク 14 の形。`/status` `/history` `/recent` `/snapshot` … の他の鍵と並びはそのまま) |

**形を変えるとき (鍵を消す・意味を変える・入れ子を変える) は `SCHEMA` を +1 して、この表に
1 行足す決まりです。鍵を末尾に足すだけなら上げません** (読む側は知らない鍵を無視できるので、
版を上げると「変わっていないのに分岐が増える」ことになります)。


`/status` のトップレベルの `version` には動いているバイナリの版が出ます (`-V` と起動ログと同じ文字列)。
末尾の `build` はビルドの種類 (`release` / `dist` / `debug`。T28.42) です。

**`/status` は 2 つの窓が混ざっている**ので、どちらの窓かが分かるように目印を出します:
`since_start_secs` から下 (`total_requests` / `bytes_forwarded` / `cache_hits` …) は**この起動から**、
`hosts[]` と `clients[]` は状態ファイルに残る**通算**で、`restored_since` がその通算の始まり
(最も古い `last_seen` の epoch 秒。`0` なら表が空) です。あわせてプロセス全体の数え物
`threads` (`/proc/self/status` の `Threads`。接続スレッドだけを数える `live_threads` とは別で、
監視・履歴・接続試行のスレッドも入ります) と `fds` / `max_fds` (`/proc/self/fd` の数と `RLIMIT_NOFILE`) も出ます。
`/proc` を読むのは **`/status` と `/metrics` に来たときと 5 秒ごとの履歴の標本のときだけ**です。
ただし **`boot`** (`id` = `/proc/sys/kernel/random/boot_id`、`pid` = このプロセスの PID) は
**起動に 1 回だけ**読みます (値はプロセスの生存中に変わりません。読めない環境では `id` が `null` で、
`/status` は落ちません)。**`id` が前の起動と変わっていればホストの再起動、同じならプロセスだけの再起動**
なので、`/events` の `start` の直前に `shutdown` が無い起動 (無言の再起動) をこの 2 つに切り分けられます
(T24.0。`/events` の `start` の文面にも `boot` の先頭 12 文字が入ります。1 件 128 B の枠のため)。

`/status` には上限といまの混み具合も出ます: `max_conns` / `max_threads` (`auto` で決まった値。`0` は無制限)、
`live_threads` (生きている接続スレッド) / `idle_threads` (そのうち仕事待ち) / `queued_jobs` (上限に当たって
待たせている仕事。捨てていません)。`auto` が何を選んだかは起動ログを見なくてもここで分かります。
同じ 5 つは `/metrics` にも gauge で出ます (`sorahost_max_connections` / `sorahost_max_threads` /
`sorahost_threads{state="live"|"idle"}` / `sorahost_queued_jobs`)。
**接続スレッドの 2 つはラベル付きの 1 系列にそろえました**。旧名 `sorahost_live_threads` /
`sorahost_idle_threads` も**残してあります** (はじめは 1 版だけのつもりでしたが、消す理由が無いので両方出し続けます。T28.23)。新しく組む監視はラベル付きの方を使ってください。
`/metrics` にはこのほか `sorahost_connect_seconds`(`_bucket{le=}` / `_sum` / `_count`。CONNECT 確立の
ヒストグラム。区間は `/history` と同じ 12 段。**繋がった CONNECT だけ**を数えます — T20.4。`0.18.0` までは失敗した 1 本も入っていました)、`sorahost_dns_seconds_sum` / `_count` (名前解決のミスに
かかった時間)、`sorahost_errors_total{cause="dns|refused|unreachable|timeout|reset|tls|loop|other"}`、
**`sorahost_rejected_requests_total{reason="request_line|header_too_large|method|no_host|bad_uri|body_framing|obs_fold|dup_host|bad_header|header_timeout"}`**
(読めずに 400 / 408 / 414 / 431 で断った要求。10 本で固定。T14.28。`header_timeout` は T29.10)、
**`sorahost_silent_closes_total`** (1 バイトも来ないまま `PROXY_HEADER_TIMEOUT_SECS` を過ぎ、408 を返さずに閉じた先張りの接続。T33.0)、
`sorahost_fds` / `sorahost_max_fds` / `sorahost_process_threads`、
**`sorahost_rtt_seconds_sum` / `_count`** (`{side="client"|"origin"}`。カーネルの平滑化 RTT。
標本は接続 1 本の終わりに 1 つで、ホスト別は出しません) が出ます。

**`sorahost_errors_total` には DNS の失敗の内訳も出します** (T26.1)。`cause="other"` の**うしろ**に
`cause="nxdomain"` (`EAI_NONAME` など = 引き直しても変わらない) と `cause="dns_temp"` (`EAI_AGAIN` = 引き直せば
変わりうる) が並び、値は `/status` の `errors_by_cause` の 9・10 番目と同じです (系列の名前・HELP・先頭 8 つの
並びは変えていないので、既にある式はそのまま使えます)。`dns` (合計) が動いていても**リゾルバの一時的な失敗なのか、
名前が無いのか**を監視側から切り分けられるようにするためで、まだ 1 件も無い内訳は行ごと出しません
(0 を出すと「見えている」と読めてしまうため。`host_blocked_total` と同じ約束です)。

**起動の切り分けと heap の基準も `/metrics` に出します** (T25.3)。`sorahost_boot_id_info{id="…"}` は
`/status` の `boot.id` と同じ値 (`/proc/sys/kernel/random/boot_id`) を **info 型** (値は常に `1`) で出したもので、
「ホストが起動し直すと変わる・プロセスだけの起動し直しでは変わらない」はここでも同じに読めます。
**ラベルは `id` の 1 つだけなので系列は 1 本**で、増えるのはホストを再起動したときだけです
(読めない環境では行ごと出しません — 0 や空の `id` を出すと「起動が変わっていない」と読めてしまうため。
`sorahost_kernel_*` と同じ判断)。
**版とビルドの種類も 1 行**: `sorahost_build_info{version="0.29.35+b2b26c1",build="release"} 1` (T29.19。`/status` の
`version` と `build` (T28.42) と同じ値の **info 型**。版を入れ替えると古い系列は止まるので、監視から「いつ版が変わったか」が読めます)。
heap は `sorahost_heap_bytes` (いまの値。`/status` の `memory` と同じ `heap_used + mmap − cache_memory`)、
`sorahost_heap_baseline_bytes` / `sorahost_heap_baseline_at_seconds` (起動 60 秒の基準と、それを取った epoch 秒で、
`/status` の `memory.baseline` と同じ値) の 3 本で、**増えは `sorahost_heap_bytes − sorahost_heap_baseline_bytes`** です。
基準の 2 本は、まだ 60 秒たっていない起動・`mallinfo2` が読めない環境・状態ファイルを開いていない
(`PROXY_STATS_PERSIST=off` / `--lite`) では出しません (`/status` が `baseline: null` になるのと同じ判断)。
**Prometheus に出すのは、起動ごとの 60 秒の値が時系列として残るから**です: `/status` は「いまの起動」の
基準しか持たず (前の起動の値は状態ファイルに残っても読まない — T24.4)、版を上げたときに起動直後の heap が
増えたかを比べられるのは監視側だけです。基準の 2 本だけでは**増え**が読めない (いまの heap が `/metrics` に
無い) ので、`sorahost_heap_bytes` も出しています。
ホスト別の応答時間ヒストグラム (`sorahost_host_request_duration_seconds`) は区間が 24 段になったので
**上位 50 ホストまで**です (数え上げの系列はこれまでどおり上位 100 ホスト)。ダッシュボードの「接続中」にも
`スレッド 7 / 256 (空き 3) · 接続上限 1008` の 1 行が出ます。数えるには接続スレッドで共有している鍵が要るので、
**`/status` と `/metrics` に来たときだけ**数えます (要求ごとの仕事は増えません)。
`cache` の `revalidations_dropped` は、上限に当たって捨てた裏側の再検証の数です
(こちらは「後でやればいい仕事」なので待たせません)。`cache` の `not_stored_rotations` は
「保存されないと分かった URL」の記憶 (ブルームフィルタ) を入れ替えた回数です。

**Grafana で段階と待ちを見る**: `/profile` の段階は `/metrics` にも
`sorahost_stage_seconds{kind="connect"|"forward",stage=...}` の `_bucket{le=}` / `_sum` / `_count` として出ます
(CONNECT 7 段 = `queue` / `client_read` / `dns` / `connect` / `first_relay` / `relay` / `park`、
転送 6 段 = `queue` / `client_read` / `origin` / `send` / `ttfb` / `body`。区間は `/history` と同じ 12 段 + `+Inf` で、
`le` も `_sum` も**秒**)。**累計は起動から**です: Prometheus のヒストグラムは単調増加が前提なので、
`/profile` の窓 (1 時間 / 1 日で古い標本から落ちる) の和ではなく、起動からの累計を別に持っています
(再起動で 0 に戻るので、`rate()` / `histogram_quantile()` はそのまま使えます)。段階が累計に入るのは
**5 秒ごと**なので、最後の 5 秒ぶんは次の収集で入ります。**`--lite` では段階を測っていないので 1 系列も出ません**
(`sorahost_kernel_*` と同じ判断で、源が無いときに 0 を出しません)。**ホスト別には出しません**
(系列が増えすぎるため。ホスト別は `/hosts` と `/status` の `hosts[]` で見ます)。
あわせて `sorahost_warm_names` (keep-warm で裏から引き直し続けている名前の数。gauge) と
`sorahost_lock_contention_total{lock="stats"|"dns"|"park"|"workers"}`
(そのロックを取るときに**本当に待たされた**回数の累計。counter) が出ます。
canary の `sorahost_canary_seconds{stage="dns"|"connect"|"ipv6_connect"}` (最後の値。
`ipv6_connect` は**繋がった回だけ**出ます = 行が消えていること自体が「IPv6 が死んでいる」の印) と
`sorahost_rtt_seconds_sum` / `_count{side=}` は前からあるものです。
段階の 13 本で `/metrics` は **約 14 KB 増えます** (ホスト表と接続元表が満杯のときで 243 → 257 KB。上限は 400 KiB)。

`/status` の `hosts` にはホスト (`scheme://host:port`、CONNECT は `connect://host:port`) ごとの要求数・ヒット・ミス・
バイパス・エラー・バイト数が要求数順に最大 50 件入ります。表は 1,000 ホストまでで、**満杯のときに新しいホストが来ると
`last_seen` (最後に使われた時刻) のいちばん古い行を 1 つ捨てて入れます** (T32.10。捨てた行の通算は `other` の行に足すので、
表を足した合計は減りません。捨てた数は `/status` の `hosts_evicted`)。前は満杯になると新しいホストが全部 `other` に入り、
tokyo の 0.30.4 では窓の要求の 76.5% が `other` で見えず、`/slo` の宛先外し (T30.4) も効きませんでした。
バイト数は合計 (`bytes`) のほかに**向き別の `bytes_in` / `bytes_out`** が並びます (T14.26。`bytes_in` =
クライアント → オリジン = 上り、`bytes_out` = オリジン → クライアント = 下り)。上り主体の相手 (ログ送信) は
「利用者の回線の上り」が律速で、プロキシでもオリジンでもない — その切り分けに使います。
**CONNECT は `bytes == bytes_in + bytes_out`** ですが、**forward の `bytes` は今までどおり応答のぶんだけ**なので
(欄の意味は変えていません)、要求本文のある相手では `bytes_in + bytes_out` の方が大きくなります。
数え直しはしていません (中継が方向ごとに持っている値と、要求本文 / 応答のバイトをそのまま渡すだけです)。
**`?sort=requests|errors|dns|slow` でこの 50 件の切り出し方を変えられます** (既定は `requests` = 今までどおりの要求数順。
`errors` はエラー件数、`dns` は名前解決に費やした合計 `dns_ms_sum`、`slow` は応答 (CONNECT は確立) の平均 `avg_ms` の
多い / 遅い順。**知らない値は既定に倒します**)。JSON の形も件数も変わらず、変わるのは `hosts[]` の並びだけです
(`clients[]` は要求数順のまま、`/healthz` は問い合わせを読みません)。要求数の上位 50 には「悪いホスト」が出てこない
のが動機で、デプロイ先の実測 (58.6 時間) では**エラー 99 件のうち 80 件 (名前解決の失敗) を抱えたホストが
1 つも上位 50 に居ませんでした**。`curl "http://127.0.0.1:8080/status?sort=errors"` で見られます。

**`?hosts=0` で `hosts[]` を丸ごと省けます** (T25.1)。既定 (書かない・`1`・知らない値) は今までどおりで、
消えるのは `hosts` の鍵だけで、**ほかの鍵も `schema` も 1 バイトも変わりません**。`/status` の応答は
`hosts[]` が 8 割を占め (2026-10-23 の実測で 33,280 B のうち 26,917 B。手元の模型 50 宛先でも
25,182 B のうち 19,351 B)、**行は 50 件で頭打ち**なものの、1 行あたり最大 538 B
(エラーや名前解決の欄が埋まった行) まで太ります。30 秒ごとに引く監視ではこの `hosts[]` が効いてくるので、
**ポーリングする監視は `curl "http://127.0.0.1:8080/status?hosts=0"` の軽い形を使ってください**
(同じ模型で 5,831 B = 77% 減)。`hosts[]` の中身が要るときは `/hosts` を `sort=` `limit=` `offset=` で
別に引けます。1 要求で全部取る `/snapshot` の `parts` と各部の形は今までどおりで、この問い合わせの
影響を受けません。
ホスト別の行にはさらに**待ちの内訳**が入ります: `dns_ms_sum` / `dns_misses` (名前解決を OS に聞いた合計時間と回数)、
`connect_ms_sum` (接続にかかった合計時間。名前解決のぶんは含みません)、`v4_wins` / `v6_wins` (確立した族)、
`errors_by_cause` (`[dns, refused, unreachable, timeout, reset, tls, loop, other, nxdomain, dns_temp]` の順の件数。
**先頭 8 つは今までどおり**で、9・10 番目が `dns` の内訳 (`nxdomain` = 名前か住所が無い =
引き直しても変わらない / `dns_temp` = 一時的な失敗 = 引き直せば変わりうる。`dns` は合計のまま
残るので `dns == nxdomain + dns_temp`)。T25.0 より前の雪像は 8 要素なので、9・10 番目が
無ければ `dns` の合計だけを読んでください。
`loop` は自分の `Via` が付いて `508` で閉じたもの。**複数の候補を並行に試して (Happy Eyeballs)
締め切りまで 1 本も確立できなかったときは `timeout`** です — 2026-09-18 より前は、その間に 1 本だけ先に
返ってきた `ECONNREFUSED` などが最後のエラーとして残り、締め切りいっぱい待った接続が `refused` に
数えられていました。T15.0。**オリジンの応答を `PROXY_TIMEOUT_SECS` 待っても先頭が届かなかったときも
`timeout`** で、ログは `origin response timed out after N s` です — 0.27.8 までは Linux の締め切りが返す
`EAGAIN` を `other` に数え、`failed to read origin response: Resource temporarily unavailable (os error 11)`
と出していました。T28.5)、**`rtt_ms`** (`{"avg":…,"min":…,"samples":N}`。
カーネルの平滑化 RTT (`TCP_INFO`)。標本は**接続 1 本の終わりに 1 つ**なので `timed` (要求数) とは数が合いません。
1 本も閉じていなければ `null`) と **`retrans`** (その接続たちが再送したセグメントの通算)、
**`sni_mismatch`** (そのホスト宛ての CONNECT で、宛先のホストと覗いた SNI が食い違った本数。
T14.38。**メモリだけ**なので再起動で 0 に戻ります。合計は `/status` の末尾の `sni_mismatches`)、
**`syn_retrans`** (そのホストへ繋ぐときに **SYN を送り直した回数の合計**。T14.46。確立の直後に
`TCP_INFO` を 1 回読んだ値で、`retrans` (接続の終わりに読んだ通算) と違って**確立の失敗だけ**を数えます。
1 回で確立が約 1 秒、2 回で約 3 秒よけいにかかるので、`avg_ms` が飛んでいるホストはここを見てください。
**メモリだけ**なので再起動で 0 に戻ります。合計は `/status` の末尾の `syn_retrans_total`)。
**測るための費用は熱い経路に乗せていません**:
名前解決の時計はキャッシュを外したときだけ読み、内訳はホスト別統計が既に取っている鍵の内側で足します
(原子操作もシステムコールも増えません。実測: forward の確保 8.03 → 8.03 回/要求、
`--lite` のシステムコール 5.00 → 5.00 回/要求)。`dns` には `miss_ms_sum` / `miss_avg_ms` (ミス 1 回の値段) と
`refreshes` (期限前に裏で引き直した回数) / `negative_ttl_secs` (失敗を覚えておく秒数) /
`warm_secs` (keep-warm の窓) / **`warm` (いま warm な名前の数)** /
**`changes` (引き直しで答えの集合が変わった回数の合計)** が出ます。
**裏の引き直しはミスに数えません** (利用者は待っていないので、`misses` と `miss_avg_ms` に混ぜると
「ミス 1 回の値段」が読めなくなる)。`/metrics` では `sorahost_dns_lookups_total{result="refresh"}` です。
さらに **`misses_by_kind`** (ミスの内訳。`cold` = 表にまだ答えが無い / `expired` = 答えは持っていたが
TTL を過ぎた / `warm_stale` = **warm なのにミスした** = 裏の引き直しが間に合っていない /
`negative` = 覚えている失敗の期限が切れたので引き直した。**4 つの和は必ず `misses` と一致します**) と、
裏の引き直しの様子 **`refresh_failures`** (引き直しが失敗した回数) / **`refresh_ms_sum`** /
**`refresh_ms_max`** (引き直しの `getaddrinfo` にかかった時間の合計と最大 ms) /
**`refresh_late`** (予定の時刻から **5 秒以上**遅れて始まった引き直しの回数。引き直しは
`dns-refresh` スレッド 1 本が順にやるので、1 回 約 2 秒かかる名前が続くと後ろが詰まります。
要求の経路が頼んだ先回りは予定の時刻を持たないので数えません) が出ます。
末尾の **`warm_evicted`** (T16.0) は warm の枠 (同時に 32 件) が満杯で、新しく warm になる名前のために
**最後の使用がいちばん古い名前を外した**回数の起動からの通算です (`/history` の `dns_warm` は 5 秒ごとの瞬間値なので、
枠が埋まって押し出しが起きていたかはこれで読みます)。**要求の経路の例外**: 数えるのはその名前が窓の中で 2 回目に
使われ、かつ枠が満杯のときの枝だけで、既に握っている鍵の内側の原子の加算 1 つです (システムコールも確保も増えません)。
**読み方**: `expired` が主なら窓 (`PROXY_DNS_WARM_SECS`) の外で期限が切れている =
窓を延ばすと効く、`warm_stale` が出ていれば引き直しが間に合っていない = 窓ではなく
`refresh_failures` / `refresh_late` を先に見る、という順で読みます (どちらに手を入れるかは
この内訳でしか決まりません)。
`clients[]` にも同じ `rtt_ms` / `retrans` が出ますが、**こちらはクライアント側** (利用者 → プロキシの往復) です。
`bytes_in` / `bytes_out` も同じ向き (`bytes_in` = その端末が上げた量) で出るので、「この端末は上りが主か下りが主か」が読めます。
`/status` の `clients[]` には接続元 IP ごとの要求数・転送量・拒否数・応答時間が要求数順に最大 50 件入り、
末尾に **`first_seen`** (初めて見た時刻。`0` = この起動より前から居る) / **`agent`** (最後に見た `User-Agent` 1 つ。
無ければ `null`) / **`distinct_targets`** (宛先ホストの種類) / **`literal_targets`** (IP リテラル宛ての要求数) が付きます
(既存の欄の順は変えていません)。`User-Agent` を読むのは**接続の最初の要求だけ**で、2 要求目からは旗で飛ばすので
要求ごとの費用は 0 です (`--lite` では読みません)。全接続元と残りの欄は `/clients` で見られます。
`/metrics` も同じ内容を `sorahost_*` 系列で出します。`origin_connections` にオリジンへの新規接続数と再利用回数、`cache` には各層の `used_bytes` / `limit_bytes` (現在の予算) / `reserved_bytes` (バラスト) /
`keep_free_bytes` (動的マージン) / `mode` (`auto` か `fixed`)、メモリの層の末尾に本文の確保の大きさ (`Vec::capacity`) の合計 `alloc_bytes` (T35.11。`used_bytes` は長さの和で、長さの分からない本文も保存の最後で縮めるので、ふつうは同じ値) と、`system` に直近の計測値 (メモリ総量と空き、
活性ページキャッシュ、cgroup 制限と使用量、PSI の有無、ディスク総量と空き、自プロセスの RSS) が入ります。

- **RSS の内訳** (`/status` の `memory`。T14.21): 256 MiB のコンテナで「RSS が何でできているか」
  (ヒープの断片・スレッドのスタック・キャッシュ・記録のリング) を 1 枚から読むためのものです。
  **読むのは `/status` に来たときだけ**で、要求の経路には 1 命令も増えません
  (`mallinfo2(3)` はアリーナの鍵を順に取るので数 us かかります)。
  - `heap_used` / `heap_free` / `mmap` は glibc の `mallinfo2(3)` の `uordblks` / `fordblks` / `hblkhd`。
    **glibc 2.33 以上でだけ読めます**: リンク時に決め打ちせず `dlsym(RTLD_DEFAULT, "mallinfo2")` で
    実行時に探すので、musl や古い glibc、Linux 以外では落ちずに 3 つとも `null` になります
  - **返していない空き (`heap_free`) は 1 時間に 1 回 OS へ返します** (T29.25)。glibc の `free` はヒープの
    天辺の空きしか返さないので、間に使用中の塊が残るとその下の空きページが RSS に居座ります (0.28.48 の
    24 時間で RSS 65.8 MB のうち `heap_free` 18.3 MB)。履歴スレッドが `heap_free > heap_used` のときだけ
    `malloc_trim(0)` を呼び (1 MiB 以上返したら info のログ 1 行。手元の 400 並列のあとで 40 → 33 MiB、
    1 回 1.2 ms)、返したページは空きの塊のままなので **`heap_free` の数は減らず、減るのは `rss`** です
    (**`heap_free` は返した頁を含みます**。常駐している空きはこれより小さく、手元の trim 後で `heap_free` 11.6 MB に対し約 5.7 MB)。
    `malloc_trim` も `mallinfo2` と同じく実行時に探します。履歴スレッドの無い `--lite` /
    `PROXY_STATS_PERSIST=off` では返しません
  - **256 KiB 以上の確保は `mmap` に出ます** (T32.3。`PROXY_MALLOC_MMAP_THRESHOLD_KB`)。glibc の閾を起動時に固定するので、
    重い口の `String` やキャッシュの本文はアリーナでなく `mmap` に数えられ、free した時点で OS へ返ります。
    0.30.4 までと比べると `heap_used` が小さく `mmap` が大きく出ますが、**`heap_used + mmap` は同じ**なので、
    締めの heap の行 (`heap_used + mmap − cache_memory` と起動 60 秒の基準の差) は読み方を変えずに比べられます
  - `rss` は `/status` を組むときに `/proc/self/status` から**今読んだ** `VmRSS` です (T32.4)。
    末尾の `rss_anon` / `rss_file` / `rss_shmem` は**同じ 1 回の読み**の `RssAnon` / `RssFile` / `RssShmem` で、
    足すと `rss` になります (`rss_file` は本体と libc・libcrypto などの共有ライブラリの頁で、手元で約 5〜9 MB。
    ほかのどの欄にも出ていなかった分です)。0.30.4 までは `rss` がキャッシュのプローブの値 (= 同じ応答の
    `cache.system.process_rss_bytes`) で、**起動直後はプローブが起動中に読んだ古い値** (起動 3 秒で 4.76 MB、
    そのときの VmRSS は 25.9 MB) でした。プローブの値は今までどおり `cache.system` に `probed_at` 付きで出ます
  - `stacks_estimate` は**予約**の合計です (接続スレッド `conn` は 256 KiB、それ以外は Rust の既定 2 MiB)。
    **常駐しているのは末尾の `stacks_resident`** (T32.4) で、`/proc/self/maps` のスタックの写像 (主スレッドの
    `[stack]` と、下端に番兵の頁が接した名前の無い `rw-p`) の常駐の頁を `mincore(2)` で数えた合計です
    (1 本 8〜28 KiB。tokyo の `stacks_estimate` 22.0 MB に対し常駐は 1 MB 未満とみられます)。smaps を読まないので
    `/status` 1 回の増えは 0.3 ms 未満。Linux 以外は `null`
  - `cache_memory` はキャッシュがヒープに持っている量 (`cache.memory` の `used_bytes` +
    先行確保の `reserved_bytes`)。本文は長さで数えます。確保の大きさ (`Vec::capacity`) の合計は `cache.memory.alloc_bytes` に別に出ます
    (T35.11。長さの分からない本文も保存の最後で縮めるので、ふつうは `used_bytes` と同じ)
  - `rings` は記録のリングが**満杯になったときの見積もり** (バイト): `recent` (2,000 件)、
    `errors` (500 件)、`bursts` (50 枚)、`log` (1,000 行)、`events` (512 件)、
    `trace` (1,000 行。T14.27)、
    `history` (**5 秒 × 4,320** + 60 秒 × 1,440 + 1 時間 × 720 の標本と、閉じた接続の窓、
    速さと半閉じの窓。5 秒の標本を 6 時間ぶん持つので 2.95 → 4.77 MB (T14.32)、
    T15.0 で標本 1 本が 504 → **664 B** になって **5.84 MB**、T16.0 で **688 B** / **6.00 MB**、T28.45 で **824 B** / **6.88 MB**、T29.12 で **952 B** / 約 **7.7 MB**)、
    `hostseries` (16 ホスト × 288 標本 × 5 項目 × 8 B = 180 KiB。T14.22)、
    `readers` (内部エンドポイントを引いた接続元の表。環状ではありませんが同じ「満杯のとき」の
    見積もりで並べてあります。最大 256 行。T14.53)、
    `quantiles` (3 系統 × 1,024 本 × 8 B = 24 KiB。T14.31、T15.0 で `wait` を足して 16 → 24 KiB)、
    `profile` (段階とスレッドの窓 = 5 秒 × 720 + 60 秒 × 1,440 の標本。`.rrd` には書きません。
    T14.3。**T14.21 はこれを落としていた**ので `total` が RSS の説明に足りていませんでした。
    T15.0 で足して 6.77 MB、T16.0 で 6.95 MB — `/profile` の標本 1 本は 3,216 B で、`history` より大きい口です) と、
    その合計 `total` (この機械では **14.3 MiB** = 15,022,620 B。T16.0 の前は 14.0 MiB)
  - `rings_used` は `rings` と**同じ鍵**で、**いま埋まっているぶんの実バイト** (T15.0)。
    1 件あたりの見積もりは `rings` と同じものを使うので、必ず `rings_used.<名前> ≤ rings.<名前>` です。
    `rings` は 0 時間でも 36.6 時間でも 1 バイトも変わりませんが、こちらは溜まるにつれて増えます
    (起動直後はほぼ 0)。割合は出しません (`used ÷ capacity` で出せますが、割合からは実バイトを戻せません)。
    件数そのものは `/recent` や `/errors` の `total` を見てください
  - `arenas` は `PROXY_MALLOC_ARENAS` で実際に掛けた `M_ARENA_MAX` (`0` = glibc の既定のまま)
  - `rings_touched` (bool。T17.8) は、起動時にリングの置き場を満杯のぶん確保して 1 ページに 1 バイトずつ
    触ったか。`true` なら **RSS は起動直後から天井の近く**に居るので、そこから増えたらリングが埋まった
    せいではなく、そのまま「増えた」の信号として読めます (この機械で 12.9 MiB を 3〜5 ms。満杯にしても
    RSS は +36 KiB。触らなければ満ちるまでの 1 日で約 12 MiB 増えていました)。触るのは `history`
    (`PROXY_STATS_PERSIST=off` では触らない) と `profile`、`recent` / `errors` / `bursts` / `events` / `log`
    の 1 件の固定部 (`PROXY_RECORDS=off` では触らない) で、文字列は来たときに確保します。`trace`・
    `hostseries`・`quantiles` は使い始めに 1 回だけ確保する作りのまま触りません。触っても件数は
    増えないので `rings_used` は変わりません。**`--lite` と Linux 以外は `false`** (今までどおり満ちるまで伸びる)
  - `baseline` (T24.4) は、**起動から 60 秒たった時点**の `heap_used + mmap − cache_memory` を
    `{"at":…,"bytes":…}` で出す欄です (状態ファイルの末尾の領域に**1 回だけ**書くので、`/status` を
    何度引いても動きません)。**その起動の値だけ**を出すので、起動し直すと (ホストの管理者による
    再起動でも) 60 秒たつまで `null` です。`mallinfo2` が読めない環境と `PROXY_STATS_PERSIST=off`
    (`--lite`) も `null`。**heap が増えたかはこの値との差で読める**ので、0 時間の雪像を撮らなくても
    起動ごとに判定できます (判定表の phase24 の heap の行は、これがあればこれを使います。T24.2)
  - `trim` (T30.1) は、1 時間に 1 回の `malloc_trim(0)` (T29.25) の通算です:
    `{"count":…,"skipped":…,"last_at":…,"last_returned_bytes":…,"total_returned_bytes":…,"last_us":…,"every_secs":3600}`。
    `count` は呼んだ回数、`skipped` は 1 時間たったが `heap_free ≤ heap_used` で呼ばなかった回数、
    返した量は前後の RSS の差 (`heap_free` は返しても減りません)、`last_at` は epoch 秒です。
    呼んだことが無ければ `last_*` は `null`。`PROXY_STATS_PERSIST=off` (`--lite`) では `history` スレッドが
    動かないので、同じ形のまま 0 と `null` です

  **足して RSS になる形ではありません**: `heap_free` は「アロケータが返していない」だけで常駐しているとは
  限らず (`MADV_DONTNEED` 済みのページ)、`mmap` も確保しただけで触っていないページは常駐しません。
  「RSS のうち説明できる部分を上から並べたもの」として読んでください。
- **直近の窓の正確な分位点** (`/status` の `recent_quantiles`。T14.31):
  `{"connect":{"n":1024,"p50":0.712,"p90":1.204,"p99":3.410,"max":9.876,"window_secs":137},"forward":{…},"wait":{…}}`。
  `hosts[]` の `p50_ms` / `p95_ms` や `/history` の分位点は **区間 (ホスト別 24 段・履歴 12 段) の内側を
  線形に補間した値**で、5〜10 ms の区間に入る限り 5.0〜10.0 のどこかを返します。こちらは
  **確立時間そのものを 1,024 本そのまま**持った環状バッファから `select_nth_unstable` で出す
  **正確な値**なので、「p50 が 8.3 か 6.0 か」を 1 ms 単位で読めます。
  - **単位は ms (小数 3 桁)**。内部は **us** で持っています (`u32`)。
    ただし **forward の「初バイトまで」は元が ms 刻み**なので (`Detail::first_byte_ms`)、
    小数は 3 桁出ても刻みは 1 ms です。**CONNECT の確立だけが us の精度**で出ます
    (ベンチ (`--only connect`) の p50 と ±0.05 ms で突き合わせられるのはこちらです)。
  - `n` は環に残っている本数 (最大 1,024)、`window_secs` は**いちばん古い標本からの経過秒**
    (= この `n` 本が何秒ぶんか)。忙しければ数秒、暇なら数時間になります。
  - `connect` は CONNECT の**確立まで** (`connect://` の鍵のもの)、`forward` は forward の**初バイトまで**。
    **エラーで終わった 1 本 (繋がらなかった 502 など) は入りません** (T20.4。`/history` の分布と同じ数え方。
    `0.18.0` までの版は「失敗するまでの時間」も入っていて、繋がらない宛先への再試行が続くと p90 が秒になりました)。
    `wait` も同じで、`n` は「繋がった本数」です
  - **`wait` は利用者が待つ時間** (`queue + client_read + dns + connect` の和。**CONNECT だけ**。T15.0)。
    `connect` は要求行を読んだ**後**から測るので、accept してワーカーが動き出すまでの待ち (`queue`)
    も `Host` を読み終えるまで (`client_read`) も名前解決も入っていません。**次の「完了の定義」の
    基準線はこの `wait` を見てください**。まだ外にあるのは 2 つだけです: accept から要求行が届くまでと、
    `200 Connection Established` を書いた後のトンネル越しの TLS 握手 (`first_relay`)。
    形は `connect` / `forward` と同じ 6 つの欄で、**同じ 1 本の接続を数えるので `n` は `connect` と一致し、
    各分位点は `connect` の同じ分位点以上**になります。`--lite` では書きません
    (`queue` と `client_read` が 0 なので「4 段の和」を名乗れないため)。
    **`connect` の系列は 1 バイトも変えていない**ので、タスク 12〜14 の p50 と比べる値はそのままです。
  - 書くのは**ホスト別統計が既に取っている鍵の内側**で 8 バイト 1 回だけなので、
    原子操作もシステムコールも壁時計の読みも増えません。分位点を出すのは `/status`
    (と `/history?summary=1`) に来たときだけです。**`--lite` では 1 本も書きません**
    (`n` が 0 のまま)。メモリだけで `.rrd` には書かないので、再起動で消えます
- **起動直後の自己ベンチ** (`/status` の `self_bench`。T14.43):
  `{"at":1789558422,"forward_us":42.6,"connect_us":140.0,"cores":4,"requests":20000,"connects":2000,"secs":3,"note":null}`。
  `PROXY_SELF_BENCH=on` で起動したときだけ入り、既定 (`off`) では `null` です。
  **置いた先のコンテナの CPU で 1 要求が何 us か**を、[README](../README.md#性能) の「性能」の表と同じ物差しで出すためのもの
  (詳しくは「置いた先の CPU/要求 を同じ物差しで測る」)。`forward_us` は CPU/要求、`connect_us` は
  CPU/本 で、どちらも**プロセスの utime+stime の増分から自己ベンチ自身のスレッドの取り分を引いた値**を
  操作数で割ったものです (`clock_gettime` の `CLOCK_PROCESS_CPUTIME_ID` / `CLOCK_THREAD_CPUTIME_ID`。
  `/proc` の 10 ms 刻みでは 1.5 秒の窓に足りません)。`note` には断られた理由か、
  本数の上限で早く終わったことが入ります。**この 3 秒ぶんは他のどの口にも数えません**
  (`total_requests` も `/hosts` も `/recent` も素通し)。読めない環境 (Linux 以外) では
  数字が `null` になり `note` に理由が入ります
- **いまの転送速度** (`/connections` の各行の `rate_bps` と `/status` の `rate_bps_total`。T14.39):
  `bytes` は接続を受けてからの**累計**なので「いま誰が帯域を使っているか」が読めません。
  履歴スレッドが**5 秒ごとに全接続の `bytes` を控え**、前に控えた値との差分 ÷ その周期を
  **バイト/秒**で書きます。`rate_bps_total` はその全接続の和です。
  - **書くのは履歴スレッドだけ**で、接続を受ける経路にも中継 (splice の往復) にも 1 命令も増えません
    (中継が暇になるたびに置いている累計 `bytes` をそのまま控えるだけ)。240 本でも原子の読み書き
    240 回ぶんと表の鍵 1 回 (数 us) が 5 秒に 1 度だけです
  - 値は**直近の 1 周期の平均**なので、細かい山谷はならされます (5 秒より短い山は見えません)。
    周期 1 回ぶん (最大 5 秒) 遅れて出ます
  - **上り / 下りの別はありません**: 中継は方向別のバイトを中継スレッドの中でだけ数えていて、
    `/connections` の枠には合計しか置いていないためです (方向別にするには中継の経路に
    原子を 2 つ増やすことになるので採りません)。向き別が要るときは `/hosts` の
    `bytes_in` / `bytes_out` (T14.26。接続が閉じてからの集計) を見てください
  - keep-alive の HTTP 接続も、**応答を書き終えて次の要求を待つ直前**に `bytes` を 1 回置くので
    (T24.5)、`rate_bps` はその周期に終わった応答のバイト ÷ 周期になります。要求が 5 秒に 1 本
    より少ないと、応答が終わった周期だけ跳ねて残りは 0 に見えます (値が動くのは要求の終わりだけ)。
    `--lite` では表そのものが空なので `rate_bps_total` は 0 です
  - ダッシュボード (`/dashboard`) の「いまの接続」には**「速さ」の列**として出ます (T14.44)
