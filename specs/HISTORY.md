# specs/HISTORY.md — 仕様の経緯と測った数字

仕様 ([`SPECS.md`](../SPECS.md) と `specs/Sn.md`) は**いまの振る舞いの決まり**だけを現在形で書く (T38.4)。
決まりを入れた・変えたときの経緯 (前の版はどうだったか・なぜ変えたか・そのとき測った数字) は、仕様からはタスクの番号で指し、
運用や読み方に要るもの (と、決まりを見直すときに使う道具の読み方) をここに仕様ごとに残す。もっと詳しい記録は、そのタスクの `tasks/TNN.md` にある。

見出しは仕様の番号と題。仕様の側からは「`specs/HISTORY.md` の「S5 キャッシュ」」のように見出しの名前で指す。

## S3 スレッドと暇な接続の預かり

- 接続スレッドの使い回し: 生成と破棄のシステムコールは実測で 1 接続あたり約 16 回だった。
- スレッドの上限が無かったころは、預けた 5,000 本のトンネルが一斉に切れると 1 本ずつワーカーへ渡すので**一時的に 4,400〜4,700 スレッド**まで増えていた (閉じるのに shutdown・アクセスログ・統計が要るので、監視スレッドの中では落とせない)。上限 256 なら同じ場面で **260 スレッド・ピーク RSS 65 → 27 MB** で、閉じきるまでの時間は変わらない (0.66 秒)。
- 裏側の再検証は以前は再検証のたびにスレッドを起こしていたので上限の外にいた。
- 上限 256 での暇なトンネルの預かりの天井: 実測で 5,000 本の確立が 1.9 → 2.45 秒。短命な CONNECT と HTTP の代理は実測でも変化なし。
- `PROXY_PARK_IDLE`: 実測で暇な接続 2,000 本のとき 2,004 スレッド・RSS 68.0 MB → **25 スレッド・25.2 MB** (2026-09-08、`release`、`PROXY_MAX_CONNS=8192 scripts/cpu-per-request.sh --only idle-conns --conc 2000` の 3 回の中央値。`off` 側は同じコマンドに `PROXY_PARK_IDLE=off PROXY_MAX_THREADS=0` を足したもの)。暇なトンネル 5,000 本のとき 5,005 スレッド・RSS 93.9 MB → **68 スレッド・29.9 MB**。
- T29.23 より前は `idle-watch` が預かり 0 でも 1 秒ごとに起きていて、暇な `--lite` の CPU 51 us/s のうち 43 us/s がこれだった → 8 us/s。
- パイプの使い回し: 短命なトンネル (CONNECT を張ってすぐ閉じる) は 1 本あたり `pipe2` 2 回・`fcntl(F_SETPIPE_SZ)` 2 回・`close` 4 回を払っていたので、CONNECT 確立のシステムコールが 29.1 → 20.1 回/本、CPU/本 が 163.5 → 139.7 us になった。

## S5 キャッシュ

- 保存されないと分かった URL で合流を通さないのは、`Cache-Control: no-store` のオリジンへ 8 並列で同じ URL を叩くと 30,000 → 36,500 req/s になったため。
- T35.7 より前 (0.35 まで) は、ディスクだけの項目の `/lookup` の `size` は、ディスクの書式のヘッダー行込みのファイルの大きさだった。
- 0.30.4 まで (T32.8 より前) は `get` を GET として扱い、オリジンの `501` を GET の鍵に保存して他の利用者の `GET` に配っていた。
- 0.30.4 まで (T32.35 より前) は `Cookie: user=alice` の `you are alice` を `user=bob` が HIT で受けていた。
- 0.27.8 まで (T28.33 より前) は大文字のスキームを authority として読み、`[HTTP://…]:80` を引きに行って 502 にしていた。
- TLS を最初の `https://` オリジンで読むようにした理由 (T32.5): CA の束の解析が起動の主スレッドの 70% を占め、dlopen と合わせて RSS 約 5.5 MB を、CONNECT しか来ない置き場でも払っていた (手元で起動 3 秒の RSS 25.8 → 20.3 MB)。
- T28.10 でキャッシュキーのスキームとホストを小文字に畳んだ。もともと小文字の URL のキーは変わらないので、ディスクに残った項目はそのまま使えた。
- 0.27.8 まで (T28.10 より前) は読めない `max-age` を指示が無いのと同じに扱い、既定 TTL の 300 秒で新鮮にしていた。
- 0.27.8 まで (T28.2 より前) は 304 で期限だけを延ばし、配る先頭は古いまま (`max-age=0` のまま、など) だった。
- 0.27.8 まで (T28.34 より前) は `REVALIDATED` の `Age` を最初に保存した時刻から数えていたので、保存から N 秒たって再検証した直後の応答が `Age: N` になっていた (置き直した項目の次の HIT からは正しい値だった)。
- 0.28.48 まで (T29.0 より前) は T28.2 の書き直しが 304 の `Set-Cookie` も写して、**次の利用者の `REVALIDATED` と `HIT` (メモリにもディスクにも) に他人の `Set-Cookie` が付いていた**。`Vary: Cookie`・`private`・`no-store` も写したまま配り続けていた (期限が 0 になるだけで項目は消えなかった)。
- 0.29.35 まで (T29.6 より前) はクライアントの条件付き要求の 304 を中継するだけで、続く素の GET が古い先頭のままもう一度オリジンへ行っていた。
- 0.30.4 まで (T32.9 より前) は古い本文に 304 の新しい `ETag` を付けて配り続け、下流はその `ETag` で 304 をもらい続けていた。
- 0.30.4 まで (T32.13 より前) は裏側の再検証の 4xx でも古い表現を残し、grace の間は古い 200 を `REFRESHING` で配って、配るたびに再検証を 1 本出していた。
- 0.27.8 まで (T28.10 より前) は要求の `Cache-Control` の `max-age=0` と `no-cache` しか見ていなかった。
- 0.29.35 まで (T29.4 より前) は MISS / BYPASS の `Age` を落としていたので、`max-age=600, Age: 500` の表現を下流は残り 600 秒新鮮と読んでいた。
- 0.30.4 まで (T32.6 より前) は「URL → 表現」の表に保存を始めるたびに 1 行足して消さず、名前の違う GET を撃たれると伸び続けた。
- 0.29.35 まで (T29.5 より前) は `Content-Length: 0` の GET が毎回 `BYPASS` だった。
- 予算で追い出した理由を残す (T32.7) のは、10-31 の tokyo で、大きな転送の間にメモリのキャッシュが全部 (13.87 MB) 追い出されたのに、1 分ごとの `mem_limit` (189 → 126 → 53 MB) からは何が上限を下げたかが読めなかったため。
- ディスクの自分以外のファイルを 600 秒ごとに数えるようにした (T32.20) ときの実測: 5,000 ファイルで cache-probe 225 → 69 µs/s。

### `eager` を既定から外した理由

**256 MiB のコンテナで測ったら何も買っていなかった** (2026-09-10。`scripts/cgroup-run.sh` で再現できる)。

- バラスト無し (`off`) でもメモリ層は `limit_bytes` (197.6 MiB) まで埋まり、`oom_kill` は 0。**先に押さえなくても予算は取れる** (64 KiB × 4,160 URL を保存させた実測)
- 逆に `eager` は 192 MiB を先に押さえるので、256 MiB のコンテナに残る空きが 43 MiB しかない。そこへコンテナの中の別プロセスが 80 MiB 取ろうとすると、**1 秒周期のプローブがバラストを返す前にカーネルの OOM killer がプロキシを殺す** (同じ条件を 4 回試して 2 回。`off` / `staged` なら同じ 80 MiB でも 142 MiB でも平気で、cgroup のピークは 86〜147 MiB に収まった)
- 段階化すると、要求 0 件のコンテナの RSS は **215.9 MB → 23.1 MB**、`disk.reserved_bytes` は **2.9 GB → 0** になる (どちらも 256 MiB の cgroup で 60 秒後の実測)

## S6 名前解決

### 見積もりの道具

- 規則を変えたらミスと引き直しがどう動くかは、**`scripts/dns-replay.py SNAP.json`** がスナップショット 1 枚 (`/recent` の到着列と `/hosts_series` の助走) で見積もる (T17.5。いまの規則の値を同じ区間の `/history` と並べ、`promote` の条件を差し替えた案と比べる。`--json` で機械で読む形)。
- **「いまの規則」(`current`) は T29.17 から keep-warm を止めた模型** (`PROXY_DNS_WARM_SECS=0`・serve-stale 21,600 秒 = 0.22.6 からの既定) で、名前解決に失敗した到着 (`/recent` の `error:nxdomain` / `error:dns_temp`) は負のキャッシュ (60 秒) で回し、一致は**そのスナップショットの実機の値** (同じ区間の `/history` のミス、`/status` の `dns.refreshes` ÷ 起動からの時間) と ±30% で比べる (10-27 のスナップショット: 模型のミス 122 回・引き直し 405 回/時、実機 130 回・374 回/時)。T29.16 までの `current` (warm 3,600 秒・serve-stale なし。引き直し 2,261 回/時で「合わない」と出ていた) は `keep_warm` の名前で残り、`no_idle` と `--serve-stale` はそれと比べる。
- `--serve-stale SECS` (何度でも) で serve-stale の窓ごとの `expired` と引き直しの数も並べる (T21.3)。`--grid` は serve-stale 21,600 秒を基準に、warm の枠 16 / 64・窓 900 秒・warm をやめる・`warm_promote` の予定を答えの齢から出す、を並べ、`expired` + `warm_stale` のミスの 1 日あたりの増え・引き直しの回/時・名前ごとの最大を出す (T22.4。区間の前から居た名前を warm でない / warm の 2 通りで置く)。`--grid --series` は `/hosts_series` (上位 16 名前) だけで回す参考。
- **引き直しが「使われていない名前」で起きていないか**を名前ごとに並べるのは **`scripts/dns-idle.py SNAP.json …`** (T24.1。スナップショット 2 枚以上を渡すと、同じプロセスの 2 枚の差で `Δ引き直し` と `Δ要求` を名前ごとに出し、**1 回も使われていないのに引き直した回**を数える。`/hosts` の `requests` は状態ファイルから復元した分を含む通算なので、スナップショット 1 枚のときは差を取らずに通算のまま出し、この起動の中の使用は `/dns` の `idle_secs` で読む)。`--model` を付けると `dns-replay.py` の `Table` をそのスナップショットの `/recent` で回し、**k (3/4 TTL = 45 秒) と TTL (60 秒) のどちらが引き直しの間隔を決めているか**、および引き直しのうち**タイマー (keep-warm) で起きた割合**を出す (`--json` で機械で読む形。`dns-replay.py` の `--json` には `per_name` が増えた)。

## S7 環境変数と `.env` の読み直し

- 0.35 まで (T35.8 より前) はキャッシュの置き場を選ぶとき環境変数の `HOME` だけを見て、設定を読むだけで候補を作り `.write-test` を書いていた。

### `PROXY_CONNECT_TIMEOUT_SECS` の既定

- **既定を 5 → 3 秒にした根拠 (2026-10-26、T28.43。利用者の決定 6)**: タスク 28 の洗い出し (2026-10-25) の見積もりで、**縮む待ちは 4.6〜9.0 分/日**、**落とす成功は 0〜0.23 本/日**だった。T23.3 の戻す条件「切った成功が 1 日 1 本以上」に届かないので 3 秒にした。forward の確立も同じ値 (T28.8)。
- **既定を 10 → 5 秒にした根拠 (2026-10-20、T23.3)**: スナップショット 4 枚 (tokyo 3 枚 + nagoya 1 枚) の `connect_buckets` を数えると、**5 秒を越えて成功した確立は tokyo の 12 日ぶん 91,258 本で 0 本**、nagoya の 28 日ぶん (258,951 本、失敗も区間に入れた古い版) でも 22 本 (= 1 日 0.79 本の上限、`timeout` 18 本を引けば 4 本) だけだった。2.5〜5 秒も tokyo の 12 日で 4 本 (= 1 日 0.33 本)。一方 `timeout` は tokyo の 62 時間に 3,869 本あり、1 件 10 秒を丸ごと待っていた (**待ち 10.4 分/時 = 4.2 時間/日**)。5 秒にすると待ちが半分 (**2.1 時間/日**) になる。T15.6 が「5 秒は攻めすぎ」と言った根拠は、遠いオリジンで SYN の再送 (1 秒 → 3 秒) が重なると 4 秒台まで伸びうることだった。実測では 4 秒台の成功が 12 日で 4 本しかなく、**5 秒なら 4 秒台は切らずに残る** (切るのは 5 秒を越えた分だけ)。T23.3 のときの戻し方は `.env` に `PROXY_CONNECT_TIMEOUT_SECS=10` の 1 行。戻す条件は T23.99 で見た (3 秒でも同じ条件で見る)。
- **forward も T28.8 で確立をこちらにした**: 0.27.8 までは「forward は `PROXY_TIMEOUT_SECS` のまま」で、繋がらない宛先への forward 1 本がワーカーを 30 秒握っていた (tokyo の `/errors` に `http://10.255.255.1:80` の `timeout`・`connect_ms` 30,005 の 1 件)。見直しの根拠は tokyo のスナップショット 20 枚の `/recent` の forward の行 (重複を除いて 52 本) で、**確立の最大は 244 ms** (p50 86 ms) だった。forward の確立は CONNECT と同じ宛先の距離なので、CONNECT の 3 秒の根拠もそのまま当てはまる。
### ほかの変数

- `PROXY_CONNECT_NEGATIVE_SECS` を入れた理由 (2026-11-12、T36.8、利用者の判断): tokyo で死んだメールサーバー宛ての時間切れが 108〜127 件/時あり、1 本ごとに締め切り (3 秒) を丸ごと待たせていた。CPU は 1 本あたり約 0.2 ms と小さく (T36.0)、効くのは主に待ち。
- `PROXY_HEADER_TIMEOUT_SECS` (T28.0) の前の実測 (0.27.8): `PROXY_TIMEOUT_SECS=3` で 1 バイト / 2 秒を送ると 20 秒たっても切れない。黙った接続も 30 秒放されない。
- **`PROXY_HEADER_TIMEOUT_SECS` の既定を 10 秒にした根拠 (2026-10-25、T28.0)**: tokyo のスナップショット (`2026-10-25T203134Z`、1 時間ぶん) の `/profile` で、要求行から `Host` まで (`client_read`) は CONNECT 1,105 本で**最大 0 ms** (ヘッダーは 1 つの塊で届く)。accept から要求行までは計器に無い (`wait` の外) が、正規のクライアントは握手の直後に要求を送るので 1 RTT (tokyo の接続元は約 248 ms) で届く。10 秒はその 40 倍で、落ちた塊の再送が 3〜4 回重なっても間に合う。
- T29.10 より前は、`408` で閉じた接続の `/recent` の `reason` が CONNECT の確立の締め切りと同じ `error:timeout` で分けられなかった。
- **先張りの接続を黙って閉じる根拠 (2026-11-02、T33.0)**: 0.32.39 の tokyo の 48.3 時間で 408 が 3,415 件 (0.30.4 の 48 時間は 64 件) に増え、全部が 1 つの接続元から宛先も要求も無いまま 10 秒黙った接続だった。`/errors` の個票では波 (20.5 秒おき・88 秒おき) で来て止み、0.32.39 のままの 18 時間は 0.30.4 と同じ 1 件/時程度だった。手元で 0.30.4 と 0.32.39 に同じ 11 通りの使われ方 (先張り・502 や 400 のあとの沈黙・keep-alive・トンネル・ヘッダーの途中で止まる) を当てても 408 の数は同じで、増えはプロキシの変更ではなく使われ方 (先張りの接続) だった。先張りの接続は応答を読まないので 408 を書いても届かず、`/errors` の 500 行のうち 761 件ぶんを埋めていた。
- `PROXY_MIN_TRANSFER_BPS` (T29.34) の前の再現: 手元で `PROXY_TIMEOUT_SECS=3 PROXY_MAX_CONNS=8`、10 MiB の応答を 512 B / 0.6 秒で読むクライアント 8 本で、正常な要求が 70 秒間ずっと 503。入れたあとは同じ 8 本を 30 秒で 8 本とも切り、そのあと正常な要求が通る。1.7 KB/s で読むクライアントは 75 秒たっても切らない。
- `PROXY_MAX_THREADS=0` (無制限) は T10.5 より前の動き。
- `PROXY_ORIGIN_POOL` の既定 64 の根拠: 8 本だと 64 並列で p99 が 40 ms 台、64 本なら 10 ms 前後。
- `PROXY_PARK_GRACE_MS`: 預ける/戻すの往復は実測 18 µs/要求。

### `/slo` の読み方を変えたとき

- **T28.45 で 3 つの読み方を変えた** (綴りと `PROXY_SLO` の鍵はそのまま): 確立の 2 つは前は確立そのものの 10 / 100 ms で、tokyo (18 ms) は距離だけで外れていた。10-25 の tokyo のスナップショットの `history["5"]` (1 時間) を新しい判定で再生すると達成率は **0.061 → 0.937** だった (古い標本には窓が無いので `/recent` の個票から作り直した値)。
- **T29.12 で確立の窓から名前解決を外した** (`basis` の `connect` が `establish_minus_rtt` → `connect_minus_rtt`): 10-26 の tokyo で「確立 − RTT」が 50 ms を越えた成功 36 本は、その合計 19,789 ms のうち 15,159 ms (77%) が名前解決 (34 本がメール宛) = 確立の外れの大半がリゾルバの遅さだった。`/recent` から作り直した 5 秒の窓で再生すると、`history["5"]` と同じ 1 時間 (698 本) で確立の外れが p50 10・p95 12 → **3・4**、`/recent` の 3.4 時間で 38・41 → **11・8**。
- **T29.33 で比の 2 つを 1 時間の合計で判定するようにした**: 判定した 5 秒の 96% は確立 1〜4 本で、「新しい名前が 1 つ」「エラーが 1 件」で外れていた (0.28.48 の 27 時間で外れ 887 中 `dns_miss` 461 = 52%、外れた 32 標本は全部分母 1〜6 本。60 秒で判定し直しても `error_rate` 0.005 = 200 本に 1 件は満たせない)。5 秒ごとの判定では、エラーが確立 1 本だけの 5 秒にあると 0.5 で外れていた。
- **T30.3 で `error_rate` を 443・80 宛てに絞った** (`basis` の `error_rate` が `resolved_attempts_hourly_sum` → `resolved_web_attempts_hourly_sum`): T29.33 のあとも 10-28 の tokyo は 15 時間とも `error_rate` で外れて達成 0% (839 / 17,622 = 0.048) で、エラーの大半はメール宛 (`:993`・`:995`・`:143`) の確立の時間切れ (3 秒で切る。24 時間で `timeout` 717) と `refused` 63・`unreachable` 31 = NAT の 1 つの接続元からのメールサーバーの総当たり (使われ方) だった。443・80 に絞らない数え方なら、例の 1 時間は 104 / 1,104 = 0.094 で外れていた。
- **T30.4 で 1 つの宛先に偏ったエラーを外した**: T30.3 のあとも 0.30.3 の 10-29 の最初の 6 時間は 4 時間で外れ (16 / 2,018 = 0.79%)、443・80 宛てのエラー 16 件は全部 `pravda.me:443` の確立の時間切れ (1 つのサイトが応答しない) だった。443・80 宛ての試行は 1 時間 300〜400 本なので 2 件で閾を越える。外さなければ例の 1 時間は 5 / 405 = 0.0123 で外れていた。
- T38.4 で `/slo` の `judged` の文を `crates/metrics-slo/src/slo/judge.rs` に合わせた: 前の文は「確立が 1 本以上あった 5 秒」だけと書いていたが、繋がらなかった CONNECT しか無い 5 秒 (確立 0 本・エラー 1 件以上) も T20.4 から `error_rate` だけで判定している。
- T29.33 からダッシュボードの「今日の SLO」の内訳に今日の比の合計 (分子 / 分母) と 1 時間の合計で外した時間の数も出す。

## S21 `/history`

- `res=5` を 6 時間ぶんにした (T14.32) のは、バーストが数時間続く (T14.0 の 09-11 は 17〜23 時) のに 5 秒の解像度が 1 時間ぶんしか無く、60 秒に畳むと山の形が鈍っていたため。`n=` の既定は応答の大きさを変えないために 720 本のままにした。
- 履歴の標本 1 本の大きさ: T15.0 で 664 B、T16.0 で 688 B、T28.45 で 824 B、T29.12 で 952 B。
- `0.18.0` まで (T20.4 より前) の版は失敗も「失敗するまでの時間」で確立・初バイト・待ちの 12 列に入っていた (`connects` は試みた本数で、失敗は `connects` と `errors` の両方に居た)。IPv6 だけの宛先への再試行 (1 本 約 1.3 秒) が接続の 17% を占めた週は、確立の p95 が 2,066 ms と出て速さの物差しにならなかった (成功だけなら 66 ms)。T20.4 は列の名前も並びも `.rrd` の形も変えなかったので、そのころの再デプロイをまたぐ `/history` には両方の数え方の標本が並んだ (`t` が再起動より前の標本は古い数え方)。
- T16.0 より前は粗い解像度のゲージの平均を行の数で割って切り捨てていたので、5 秒 → 60 秒 → 1 時間の 2 段で下に偏っていた。
- `?summary=1` (T14.24) の前は、調査で `/history` を丸ごと (284 KB) 取って手元で集計していた。
- `normal_hours_only` の閾に中央値 × 3 を足した理由 (T29.13): tokyo の 0.28.48 は毎時 475〜1,760 本で、300 本だけで切ると 23 時間の全部がバーストになっていた (`samples 0, burst_samples 23` → 中央値 808 × 3 = 2,424 本で 23 / 23)。
