- [x] **T26.0 forward の 1 要求あたりのシステムコールを 1 回減らせるか (段 1 → 段 2)**
  - 目的: 「認証なし・手軽・**最速**」が目標なのに、forward 1 要求で `recvfrom` を 3 回呼んでいる (README の 5.02)。3 回のうち 1 回は要求ヘッダーを読み切る前の空振りか、本文の読み残しかを**まず数える**。減らせれば CPU/要求 40.4 us のうちカーネル時間 (30.2 us) がそのぶん下がる。
  - 変更箇所: 段 1 は計測だけ (`strace -c -f` と `scripts/cpu-per-request.sh`)。段 2 は `crates/http` / `crates/net-conn` の読み取りの形。
  - やること: 段 1 で `strace -f -e trace=recvfrom,sendto,read,write -c` を forward 8 並列 5 秒で取り、**1 要求あたりの回数とバイト数の分布**を出す (3 回のうち何回が 0 バイトか、ヘッダーの 1 回で本文まで読めているか)。段 2 は「最初の `recvfrom` を大きめのバッファで 1 回にし、ヘッダーと本文をまとめて読む」等を試し、**CPU/要求と p50 を前後交互 3 組**で比べる。
  - 受け入れ基準: 段 1 は内訳の表 (0 バイトの回数・平均バイト数・回数の分布)。段 2 は CPU/要求 −5% (38.4 us 以下) か、下がらないなら「なぜ下がらないか」の数字。**どちらでも、`cargo test --workspace` と bench の数字を出す**。
  - 結果 (2026-10-23、`3909ef8`): 段 1 の内訳は、`recvfrom` の 3 回が **クライアントの要求ヘッダー 1 回 (8 KiB のバッファに 63 B)・オリジンの応答 1 回 (32 KiB のバッファにヘッダー 92 + 本文 1024 = 1116 B)・プールの生存確認 1 回 (1 B の `recv` が EAGAIN)**、`sendto` が要求 104 B と応答 1140 B の 2 回。**0 バイトの読みは 0.02% (9/37,732) だけ**で、ヘッダーと本文は既に同じ読みで取れていた = まとめ直して減らせる読みは無い。唯一減らせる生存確認を、**再試行できる要求 (GET/HEAD で本文なし)** では省いて読み書きの失敗に任せる形にした (`Pool::get_with(host, want, verify)`。失敗は `is_stale_conn_error` で気づいて新しい接続で 1 回やり直す既存の経路)。本文ありの要求と裏の再検証は今までどおり覗く。除いたあとの strace は `recvfrom` **2.000/要求**、errors 0.0004/要求 (再試行の山は出ていない)。前後交互 **8 組** (release、8 並列 10 秒) の中央値で **CPU/要求 41.54 → 39.86 us (−4.0%、kernel −4.4%)**、p50 0.307 → 0.298 ms。**目標の −5% には届かず**、理由も数字で出た: 削った 1 回は単体 0.280 us だが実地では 1.0〜1.3 us ぶん効き、残る 4 回はどれも 1 回で足りているので**この経路の床は 4 回**。

- [x] **T26.1 `/metrics` に dns の内訳 (`nxdomain` / `dns_temp`) を出す**
  - 目的: T25.0 で `/status` の `errors_by_cause` は 10 要素になり、T25.3 で `/metrics` に `boot` と heap を足した。しかし **`/metrics` の接続エラーの系列は `ERR_CAUSES` (8) を回しているだけ** (`crates/prom/src/prom.rs:654`) なので、`nxdomain` と `dns_temp` が監視から見えない。実データでは `dns` 447 件のうち `dns_temp` は 8 件だが、**これが増えたときに気づける計器が無い**。
  - 変更箇所: `crates/prom/src/prom.rs`、README の `/metrics` の節、`crates/prom` の試験。
  - やること: 既存の `sorahost_connect_errors_total{cause="…"}` の**後ろに 2 つのラベル値を足す** (系列の名前・HELP・既存ラベルの並びは変えない)。`/status` の 9・10 番目と同じ値になることを実測で確かめる。
  - 受け入れ基準: `/metrics` の出力に `cause="nxdomain"` と `cause="dns_temp"` が出る (0 のときは出さない、既存と同じ約束)。既存の系列の行が 1 行も変わらないこと (`diff` で確認)。`cargo test -p proxy-prom`。
  - 結果 (2026-10-23、`51c966f`): `/metrics` の `sorahost_errors_total` の 8 つの `cause` の**直後**に `cause="nxdomain"` と `cause="dns_temp"` を足した (0 のときは行を出さない)。値は `/status` の `errors_by_cause[8]`/`[9]` と同じで、実測でも一致 (`[1,0,…,1,0]` → `nxdomain 1`、`[1,0,…,0,1]` → `dns_temp 1`)。series 名・HELP・既存 8 ラベルの並びは不変で、**全 `/metrics` の diff は足した 2 行と揺れる行だけ**。`dns_temp` はこの箱のリゾルバでは作れないので、`LD_PRELOAD` の getaddrinfo shim で EAI_AGAIN を 1 名前だけ注入して確かめた (`nxdomain` は本物)。`cargo test -p proxy-prom` 10 本、`dns_cause_test` も通過。**これで `dns_temp` の増加を単独で警報にできる**。

- [x] **T26.2 CI の `build-memory-find` を回して関門 (120 MB) の余裕を数字で持つ**
  - 目的: 120 MB の関門は毎回通しているが、**余裕がどれだけあるかは測っていない** (`.github/workflows/ci.yml` の `build-memory-find` は `if:` で普段 skip)。T24.8/T25.2 で `metrics-recent` の寄与が約 11 MB と分かったので、関門までの余裕を CI で定期的に数字として残したい。
  - 変更箇所: `.github/workflows/ci.yml` (skip の条件)、README の CI の節。
  - やること: `build-memory-find` を **週 1 回 (cron) か、`workflow_dispatch` で回せる**ようにし、結果 (通った最小の上限) を step summary に出す。毎 push では回さない (runner を長く占有するため)。
  - 受け入れ基準: 手で `gh workflow run` して job が走り、step summary に「通った最小 = N MB」が出る。普段の push では skip のまま。
  - 結果 (2026-10-23、`ccf45ce`): **口 (週 1 と手回し) は T11.7 で既にできていた** (`cron 17 3 * * 1`、`workflow_dispatch`、`if:` は `schedule || workflow_dispatch`)。欠けていたのは**数字**だったので、`build-memory-find` の最後で `build-memory.sh --find` の印字から拾って、**「通った最小 = N MB (関門 120 MB までの余裕 = X MB)」**・試した上限・落ちた上限・回した理由を step summary に並べるようにした。測れないときは 0 で埋めず「cgroup を作れない」と「どの上限でも通らなかった」を書き分ける。120 MB の関門と毎 push の `if:` は不変。YAML は Ruby の Psych で実パース (PyYAML はこの箱に無い)、run ブロックは `bash -n` と 3 通りの `find.txt` で検証。**actionlint はこの箱に無い**。
