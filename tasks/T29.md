- [x] **T.29.0 再検証の 304 の `Set-Cookie` を保存済みの先頭に写さない (他の利用者へ配っていた)**
  - 目的: 手元で再現 (`t29/protocol/probe5.py`): `max-age=1, ETag` で保存 → 利用者 A の再検証にオリジンが `304` + `Set-Cookie: session=SECRET-OF-USER-A` → 次の利用者 B の `REVALIDATED` と C の `HIT` (メモリ) にも同じ `Set-Cookie` が付き、ディスクの項目にも入る。保存時 (`response_policy_lines`) は `Set-Cookie` で保存しないのに、T.28.2 の `merge_not_modified` が写す。304 の `Vary: Cookie`・`private`・`no-store` も写ったまま `REVALIDATED` / `HIT` で配り続ける (`revalidated_policy` が `None` → TTL 0 になるだけで項目は消えない)。
  - やること: `merge_not_modified` (`crates/msg/src/headers.rs` 426 `NOT_UPDATED_BY_304`・435) で `Set-Cookie` / `Set-Cookie2` を写さない。304 が保存できない形 (`response_policy` が `None`) なら延命せず項目を消して取り直す (`crates/http/src/http/mod.rs` 1109-1137、`refresh.rs` 186-195、`crates/freshness/src/freshness.rs` 155)。304 の `Set-Cookie` を再検証した要求のクライアントにだけ渡すか落とすかを決めて README に書く。
  - 受け入れ基準: 上の 4 形 (Set-Cookie・Vary: Cookie・private・no-store) の結合テストで、他の利用者の応答と保存した先頭に 1 つも入らない。
  - 結果 (2026-10-27、`6372be0`): `merge_not_modified` の写さない名前に `Set-Cookie` / `Set-Cookie2` を足し、保存済みの先頭に残っていた写し (0.28.48 までの分) も次の再検証で落とす。304 の `Set-Cookie` は新しい `headers::with_set_cookies` で**再検証した要求のクライアントにだけ**渡す (裏の再検証では誰にも渡さない。README に書いた)。新しい `freshness::not_modified_forbids_storing` (`no-store`・`private`・`Accept-Encoding` 以外の `Vary`) が真なら、同期の再検証は項目を消してその要求にだけ 304 のヘッダーを載せた写しを配り、裏の再検証は消すだけ。ついでに見つけた穴: `revalidated_policy` が 304 の `Set-Cookie` を数えて `response_policy` が `None` になり、`max-age=600` の 304 でも TTL 0 になっていた → 数えないようにした。先頭を差し替えると `size` が合わず本文が 0 バイトで配られるので `CachedResponse::replace_head` を足した。結合テスト `tests/revalidate_cookie_test.rs` 6 本 (Set-Cookie のメモリ・ディスク、`Vary: Cookie`・`private` (ディスク)・`no-store`、裏の再検証の `no-store`) は直す前に 6 本とも落ち、直した後に通る。全体は既知の環境だけの 6 本 (canary ×4・`--check`・`errors_by_cause`) のほかは通る。版は 0.29.0 (`5d5db34`)。tokyo に前の版が写した `Set-Cookie` が残っていても、その項目の次の再検証で落ちる。
